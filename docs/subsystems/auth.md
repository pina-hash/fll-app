### Auth

THREE populations, one Auth instance. The boundary for all of them is `0002`'s trigger on `auth.users` (replaced in `0010`); everything in the dashboard is a convenience. PARENTS ARE NOT A FOURTH POPULATION: they hold no identity at all (see below).

- **Mentors:** Google only, boscotech.edu only. First sign-in inserts the `mentors` row; any other Google domain, or any email-provider account, is refused inside the insert, which aborts GoTrue and the sign-in. The first mentor row is the admin (under an advisory lock). `is_admin` is edited by admins through RLS; `_mentors_guard_update` stops self-demotion, self-deactivation and demoting the last admin.
- **Students:** no real email. Two doors, both minting the same three rows behind the same `fll.creating_student` flag: `student_create` (mentor-only RPC) writes `auth.users` + `auth.identities` + `students` in one transaction, raising a transaction-local flag (`fll.creating_student`) that the trigger requires for any `@fll.invalid` address. Address = `{join_code lowercased}-{slug}@fll.invalid`; `.invalid` is RFC 2606 reserved. Slug = lowercased first name + last initial in `[a-z0-9]`, deduped per team with a numeric suffix, STORED so a rename never changes a login. PIN = 6 digits (GoTrue's 6-character minimum). The second door is `student_claim_seat` (0019), granted to `anon`, because the mentor does not know the children's names before the first Friday: they mint N empty seats on a team, hand each child a printed card carrying one short single-use SEAT CODE, and the child types that code, their own first name, last initial and grade, picks a PIN twice, and is signed in immediately. There is NO approval queue, deliberately -- a queue means twenty children waiting on one adult.
- **A SEAT IS HANDED OUT, NOT LEFT OPEN, AND THERE IS ONLY ONE ENROLMENT DOOR.** 0013's open join window (`team_join_open`, `team_join_window_open/close`, `teams.join_open_since`, `teams.join_open_meeting_id`, `student_self_enroll`) was REMOVED WHOLE in 0019 rather than left standing beside the new path, because two doors means one of them is untested on the morning it matters. A window is open to whoever holds the team code; a claim code is issued once, spent once, and voidable before it is spent. `student_claim_codes` carries the row; `team_claim_codes_issue` mints N at a time up to the cap, `team_claim_code_void` kills an unspent one, `team_claim_code_reissue` is void-and-mint in one transaction, and `team_claim_codes` is what the console lists. A SPENT CODE IS NEVER VOIDED: the student it minted is the record of what happened.
- **A CLAIM CODE IS PLAINTEXT, AND IT IS THE SECOND AND LAST EXCEPTION.** Like the parent token (0014) and unlike a PIN, it is a one-shot capability a mentor must be able to reprint for the child who lost the card, so it is a column readable by mentors and by nobody else. Do NOT extend that reasoning to anything that authenticates a person.
- **REDEMPTION SPENDS THE SEAT BEFORE IT INSERTS THE STUDENT.** `student_claim_seat` stamps `claimed_at` and `claimed_student_id` with a uuid it minted, THEN inserts the student with that id. The other order asks the cap to hold seven seats for the duration of one statement and is refused. The composite `(claimed_student_id, team_id)` foreign key is therefore `deferrable initially deferred`; that is what lets the claim name a student two statements before the student exists.
- **CHANGING A STUDENT'S TEAM IS `student_move_team` AND NOTHING ELSE.** The address is `{code}-{slug}@fll.invalid`, so a move rewrites both halves (new code, slug re-deduplicated in the receiving team), rewrites `auth.users`/`auth.identities`, and drops every session, in one transaction -- the same shape as `team_regenerate_join_code`, and warned about the same way in the console. `_students_immutable` refuses a `team_id` or `slug` change outside it. It CLEARS forward-looking rows (role and task assignments, with counts) and REFUSES on history (a blocker raised, a photo taken), because a move cannot rewrite what happened.
- **Board devices:** the spare iPad on a table. `team_board_enable` (mentor-only) mints `{code}-board.device@fll.invalid` with a 6-digit PIN and a `team_board_devices` row; the trigger accepts that address only while `fll.creating_board` is raised. A BOARD IS A DEVICE, NOT A PERSON: it reads its own team and closes its own team's tasks, and that is all. It is on no roster, holds no role, is never checked in, cannot raise a blocker as somebody and cannot upload evidence. The dot in `board.device` is what makes the address uncollidable with a student slug (`[a-z0-9]`).
- **A PIN CANNOT BE READ BACK, EVER.** It is bcrypt in `auth.users.encrypted_password` from the moment it is set, so any screen that wants to show a PIN can only show one it just minted. `src/lib/console/pins.ts` parks those in `sessionStorage` for the printable roster card. Do not add a recoverable-PIN column; the answer to a stale card is a reset.
- **PIN reset is SQL:** `student_reset_pin` writes `auth.users.encrypted_password = extensions.crypt(pin, extensions.gen_salt('bf', 10))` and deletes `auth.sessions` for the user. **Proved end to end against GoTrue v2.195** (`tests/student-auth.test.ts`: sign in, reset, old PIN refused, new PIN accepted, old refresh token dead). The admin-API fallback was not needed and does not exist.
- **The login screen** (`/login`): student types the team code -> `team_login_roster` (anon RPC: team id + name + `first_name`/`last_initial`/`slug` per active student, nothing else) -> taps a name -> PIN -> `signInWithPassword` with the address built by `src/lib/auth/student-identity.ts`, which mirrors `public._student_email` and is held to it by `tests/login-roster.test.ts`. Mentors: `signInWithOAuth({ provider: 'google', queryParams: { hd: 'boscotech.edu' } })`.
- **Server side** uses the current `@supabase/ssr` pattern: `src/hooks.server.ts` creates the per-request client, resolves claims with `getClaims()` (retried three times on a genuine error, never on a clean "no session"), resolves the **principal** with one `auth_whoami` call, and guards `authedPrefixes` (`/app`). No claims -> `/login?next=`; claims but no principal (a deactivated account) -> `/auth/error?reason=no-access`. `src/routes/+layout.server.ts` / `+layout.ts` expose `supabase`, `claims`, `principal`; `+layout.svelte` invalidates `supabase:auth` on auth state change.
- **ONE MODULE KNOWS EACH CREDENTIAL.** `PUBLIC_SUPABASE_URL` / `PUBLIC_SUPABASE_ANON_KEY` are read in exactly two places (hooks, root `+layout.ts`). `SUPABASE_SERVICE_ROLE_KEY` has exactly one reader, `src/lib/server/service-client.ts`, via `$env/dynamic/private`; do not add a second.
- **THE SERVICE ROLE FETCHES; IT NEVER DECIDES.** Its only caller (`src/routes/p/[token]/photo/[evidenceId]`) asks the DATABASE first (`parent_photo_path`, which answers only for the child that token belongs to) and uses the service role solely to sign a 60-second storage URL for the path it was handed. Any future caller keeps that order: authorise in SQL, then fetch. A service-role call that chooses who may see what is a bug.
- **PARENTS HOLD NO IDENTITY: `/p/<token>` IS A CAPABILITY URL.** No account, no password, no session, no write path anywhere. `parent_view(token)` (0014) is the whole page in one definer call and resolves one token to exactly one child; it returns NULL, never an error, for unknown, malformed, revoked, deactivated and archived alike.
- **THE PARENT TOKEN IS THE ONE PLAINTEXT CREDENTIAL IN THIS SCHEMA, AND THE EXCEPTION DOES NOT GENERALISE.** A PIN authenticates a PERSON who can be told it again out loud, so it is bcrypt from the moment it is set. A parent link is a CAPABILITY a mentor must be able to reprint in March for a card lost in October, and hashing it would make "print the parent cards" mean "kill every link on the team". It is therefore a column, readable by mentors and by nobody else, granting read-only access to one child and revocable in one tap. Do NOT copy this to anything that authenticates a person.
- **Probing reveals nothing.** A denied read is an empty result, not an error; a surface a caller may not see answers like one that does not exist.
